# История клинического содержимого

Страницы `/d/patients/:id/history` и `/m/patients/:id/history` открываются из карты пациента. Они показывают сохранённые редакции анамнеза, аллергий, препаратов, результатов обследований, обычных и исследовательских визитов, опросников, участия и событий безопасности. Для каждой редакции доступны содержимое, автор и время записи, номер редакции и отдельное подтверждение сервера. Поиск выполняется локально по содержимому; выбор клинической записи отделяет её цепочку от других записей пациента.

## Сохранение и права

Снимок полного содержимого добавляется в той же серверной транзакции, что изменение текущей клинической записи и квитанция идемпотентности. Изменение существующей редакции через публичный API отсутствует. Старые ответы сохраняют своё определение опросника, оценки и условия; новые шаблоны не меняют их задним числом. События участия и заключения по безопасности сохраняются вместе с остальным содержимым соответствующей редакции.

Читать историю может только подтверждённый врач клиники пациента. Исследовательское согласие на пол и диагнозы не предоставляет доступ к этой истории. Административная роль организации не предоставляет медицинский доступ. Идентификатор версии не является самостоятельным разрешением: сервер проверяет организацию, действующего пациента и текущую неудалённую запись. Локальный читатель проверяет ту же связь с пациентом и записью, роль, ключ и срок пространства.

При удалении записи история сразу исчезает из серверной выборки и блокируется локальным читателем. Содержимое удаляется отдельными порциями по 50 строк. При удалении пациента закрывается вся его история и действует очистка всех его клинических версий. Аудит метаданных сохраняется без клинических текстов. Это не обещание удаления резервных копий внешней платформы.

## Офлайн и конфликты

История — отдельная синхронизируемая TanStack DB-коллекция в существующем зашифрованном SQLite-пространстве пациентов. Новая локальная редакция и текущая запись входят в одну сохраняемую native offline-транзакцию. Их создание не ждёт сети или загрузки старой истории: обновление уже подготовленного пространства не блокирует клиническую работу только из-за отсутствия новой коллекции. До первой подготовки полной истории интерфейс явно показывает ограниченность локального набора. Редакции, которые не загружались и не создавались на устройстве, без сети не обещаются.

Новые операции несут уникальный идентификатор редакции и ожидаемый идентификатор предшественника для всех клинических типов. Поэтому зависимая правка не перезаписывает чужое состояние, даже если совпал счётчик ревизии. Формы также фиксируют идентификатор редакции при открытии: после отката конфликтующей ветки редактор не подхватывает чужую ревизию с тем же номером. Обе конфликтующие правки остаются в зашифрованном архиве предложений. Они не показываются как подтверждённая медицинская история и не применяются автоматически.

Область прежних коллекций и имя обработчика `clinical.apply.v1` не изменены. Старые конверты и операции без новых полей продолжают разбираться; старые квитанции `clinical.record.v1`/`v2` сохраняют прежний состав и отпечаток. Старый протокол не приобретает проверку нового идентификатора задним числом: защита по нему относится к новым операциям обновлённого приложения. Политика конкурентных старых клиентов требует отдельного управления версиями клиентов.

При первом изменении записи, созданной до версии с историей, сервер сохраняет её последнюю доступную прежнюю редакцию. Ранее перезаписанное содержимое восстановить из аудита метаданных невозможно; приложение не создаёт вымышленную историю. Текущие записи без загруженного архивного снимка показаны отдельно. Отсутствующий автор старого локального снимка отмечается явно, а не заменяется текущим пользователем.

## Проверки и границы

Тесты проверяют полные серверные снимки разных клинических типов, авторство, повторную доставку, прежний отпечаток квитанции, несовпавшего предшественника, роли и очистку 55 версий несколькими порциями. Нативные офлайн-тесты проверяют обновление пространства без подготовленной истории, сохранение и восстановление локального снимка вместе с очередью, подтверждение сервера, зависимые конфликты для обычных записей и опросников, шифрование и закрытие доступа после удаления.

Production SSR проверяется прямым вызовом обработчика, без HTTP-сервера. Реальный браузерный перезапуск, несколько вкладок и публикация Convex в облаке этой итерацией не выполнялись. История базовых полей и согласий карты описана в `docs/patient-card-history.md`; юридически значимые подписи остаются отдельной функцией.
